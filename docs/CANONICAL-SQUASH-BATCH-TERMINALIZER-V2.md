## Durable monotonic execution

For one item at a time, the journal advances through `pending`, `evidence-verified`, `retirement-adoption-intent`, `retirement-adopted`, `completion-intent`, `completion-projected`, `terminal-verified`, and `complete`. Retirement adoption is read-only: its intent records the exact terminal claim and `cloudMutation: false`, and its result records `response-loss-adopted` plus the sealed lineage proof and `cloudMutation: false`. Completion intent is durable before the sole domain effect. Classification before that effect and exact terminal verification after it adopt local response loss or block on drift.

Every phase receipt has an exact key set and value schema, its fixed plan/item/phase operation key, the immediately preceding journal digest, and its own digest. Validation reconstructs the entire predecessor chain from the authorized empty journal, phase by phase and cursor by cursor; skipped phases, invented values, extra fields, zero placeholders, reordered receipts, or a resealed fork fail. Each completed item seals the exact live terminal-prefix digest. A completed prefix is never rolled back, and a later blocked item leaves earlier terminal items intact.

The item fence binds the exact current lease digest, claim ID, task binding, capability report, plan, PR, and phase. Stable immutable evidence and the capability binding are reverified inside that fence on every resumed execution. The completion transition is deliberately one-way: `completeSession({finalize:false})` changes the lease from delivery to completing, verifies the new completion projection, and does not pretend the old lease digest still fences the transitioned state. On response loss, execution reacquires current state and adopts only the exact already-projected completion.

There is absolutely no cloud mutation route. The controller never retires a claim and never writes a cloud ledger. Its only domain mutation is the current item's task-authorized `completeSession({finalize:false})`, projecting that original local session to completion-ready at the exact protected completion main. It never writes source bytes, authored refs, PRs, auto-merge, new claims, runtime, cleanup, branch deletion, release, or deployment. Its other writes are only the external strict journal.

The batch receipt is `completion-ready`, not cleaned, and is rebuilt exactly from the completed journal. It emits the same eight ordered continuations as the fixed PR order. This ordinary integration is the final cleanup path; V2 cannot invoke or emulate it. Never use broad `git worktree prune` as a substitute.
